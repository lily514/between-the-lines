# Milestone 2b Plan: The AI Tutor

> Agreed 2026-10-22. This plan is frozen; where implementation diverges, see [implementation-notes.md](implementation-notes.md). 2b's branch is `feature/ai-tutor`.
> Milestone 2 has five parts: **2a** the learning engine in the terminal (f80be81), **2c** the web page (bad59de), **2d** the basics (5e3bedd), **2e** getting started (39b32b1), and **2b** the AI Tutor and the Verifier (this plan). 2c, 2d and 2e were built first because Azure wasn't set up yet.

## Context

The feedback comes from templates written in code. They are safe, but every question is worded the same way, and some of the map's text reads stiffly once it is filled in ("this one broke one"). 2b has a model in Azure AI Foundry write the wording of questions and feedback. Plain code (the **Verifier**) checks that wording against the evidence pack before the viewer sees it. If the model's text fails a check, or the call fails, the templates are used instead, so the loop never depends on Azure.

2a built the hooks 2b plugs into: the `Tutor` protocol (`tutor/base.py`), fact slots (`tutor/slots.py`: `question_values`, `feedback_values`, `fill`, `SlotError`), the question view, which leaves out every outcome fact, and `Course.tutor` in `learn/session.py`. 2c's page already shows who worded the feedback ("worded by template"), and has a waiting state for each request. **Nothing in `learn/` changes**, apart from filling the takeaway's slots.

Only one new thing touches the network, the Azure client, and the tests never use it.

**What there is to word** (after 2d; 2e added none): five concepts and twelve kinds of question:
- line-breaking passes: where to pass, lines broken, gap width;
- counter-presses: what they did, seconds to win back;
- restarts: what restart;
- offside: flag or not, who is offside, was it offside;
- fouls and cards: after the foul, why booked, why play on.

**Budget:** about 5 days, plus T8 if time allows (see "Schedule"). The hackathon closes on 2026-10-27.

**Decided (Lily, 2026-10-08):**
- The model words both questions and feedback.
- When the Verifier rejects the model's text, the model gets one repair attempt, then the template is used.
- The viewer's history in prompts is a stretch goal.
- The default Tutor is the template; the model is used only with `--tutor foundry`. That now holds for `btl serve` too.

## How it works

```
question view ──► question prompt ──► model ──► JSON {text}
 (no outcome facts,                               │
  no viewer id)                                   ▼
                                    Verifier (question checks)
                                   pass │      │ fail: reasons
                                        │      ▼
                                        │  one repair (reasons sent back) ─► Verifier
                                        │      │ fail, timeout, error
                                        ▼      ▼
                                  model text   TemplateTutor text
                                        └──────┬──────┘
                                               ▼
                          fill(slots) ─► viewer answers ─► grade ─► BKT   (unchanged)
                                               │
pack + grade + level text ──► feedback prompt ──► model ──► JSON {explanation, takeaway, misconception}
                                               ▼
                                    Verifier (feedback checks) ─► same repair / fallback path
```

## Decisions

**The model can't leak what it never sees.**
- The question prompt is built only from the `QuestionView`, through `question_values(view)`. Outcome facts and the right answer are never in it. For restart and foul questions the view already leaves out the restart's name (2d), so the prompt can't give it away either.
- A test over 40 seeds and every kind of question checks that no outcome fact's *name* appears in a question prompt, and no outcome *value* either, unless the context shows the same value. A restart's team, for example, is a club the question already names.
- The feedback prompt gets the whole pack (`feedback_values(pack, chosen)`), the concept's text at the viewer's level, its misconceptions, and whether the pick was right. That last one lets it choose between confirming and comparing. It may not say the verdict, because `Grade.verdict` already does.
- **Nothing about the viewer goes in a prompt:** no viewer id, no name, and not their club. The page marks the viewer's team itself (2e), so the Tutor never needs to know it, and cached words can be shared by any viewer who meets the same pack. All the data is synthetic and generated by us, and nothing the viewer types is ever sent, so there is no way to inject instructions through a prompt.

**The model writes slots, not numbers or names.**
- Each prompt lists the facts as `slot name → display value`, so the model can write naturally. It must cite each one as `{slot}` (for example `{answer.threat_added}` or `{box_position}`), exactly as the templates do.
- The reply is JSON, enforced with a JSON schema (structured output):
  - questions: `{text}`;
  - feedback: `{explanation, takeaway, misconception}`. After a wrong pick, `misconception` is the index of the concept's misconception that best fits the pick, or null. After a right one it must be null.
- `PROMPT_VERSION` in `tutor/prompts.py` is logged with every call, so the evaluation numbers are tied to a version of the prompt.

**The Verifier is plain code, and strict.** A false rejection only costs a template sentence; a false acceptance puts a wrong claim in front of a learner. Each check has a name, which is used as the rejection reason in logs, in the repair message and in the evaluation table:

| Check | Rule | Applies to |
|---|---|---|
| `slots` | Every slot is in `question_values` or `feedback_values`, so a question can't cite an outcome | both |
| `bare_number` | No digits or number words ("two", "half", "dozen") outside slots: every number comes from the pack. Football phrases are allowed whole: "second-last defender", "own half", "halfway", "half-time", "first half", "second half" | both |
| `names` | A capitalised word that doesn't start a sentence must appear in one of the pack's displayed facts (clubs, players) or in a short allowlist. This catches real clubs and players, and names the model invents | both |
| `vocabulary` | No betting words (odds, bet, wager, stake, tip, punt, bookmaker) | both |
| `hint` | The question doesn't mention an option: by letter, by option slot, or by a word from an option's label that the question view doesn't otherwise show (such as "corner", "penalty" or "level") | question |
| `verdict` | No verdict phrases ("correct", "wrong", "well done", "not quite", …), because the verdict belongs to the grade | feedback |
| `grounded` | Feedback cites the answer (`{answer}` or an `{answer.*}` fact) and at least one of the pack's outcome facts. After a wrong pick in a pass question (where to pass), it also cites a `{chosen.*}` fact | feedback |
| `comparison` | A sentence that compares the same fact for two options ("more", "fewer", "than") must order them as the values do | feedback |
| `misconception` | The index is one of the concept's misconceptions, and null after a right answer | feedback |
| `length` | Question ≤ 45 words; explanation ≤ 90; takeaway is one sentence of ≤ 25 words | both |

- **One `grounded` rule for every kind of question.** Every pack has an answer and outcome facts: lines broken for a pass, `restart_team` for a restart, `margin_m` and `offside_call` for offside, `box_position` and `foul_outcome` for a foul. So the rule doesn't need a case for each of the twelve kinds, and a new concept gets it for free.
- **The Verifier checks its own rules on the templates.** Over 40 seeds × every concept × every kind of question × every level × a right and a wrong pick, `TemplateTutor`'s output passes every check. If some of the map's text fails one (a "two banks of four", say), the note records it and Lily decides whether to reword the map or exempt it. The check is not quietly loosened.
- **What it can't check:** whether a football explanation is *true*, or pitched at the right level. The evaluation's hand review (T7) covers that, and it's listed in the README's honest limits.

**Repair, fallback and source.**
- `VerifiedTutor(primary, fallback, on_check)` implements `Tutor`.
- Model text that passes the checks is used. If it fails, the model is told the failed checks' names and reasons once, then the template is used.
- Timeouts, Azure errors and malformed JSON go straight to the template. A per-call time budget (`CALL_BUDGET` = 12 s, which covers the repair) keeps the worst wait bounded.
- `TutorFeedback.source` says who wrote it: `gpt-5.4-nano`, `gpt-5.4-nano (repaired)`, or `template (fallback: bare_number)`. The terminal shows it in small text under the feedback; the page already shows it in its source line.
- `on_check` receives a `CheckRecord` for every call: prompt version, attempt, passed, reasons, latency, tokens. The CLI appends these to `data/tutor-log.jsonl` (gitignored) through `io.py`.

**Wording once per question.** The web server keeps no session: each request replays the viewer's match up to the pending question (2c). So `/next` and then `/answers` would each word the same question. That means two model calls, and possibly different words between the question shown and the one answered.
- `CachedTutor` (`tutor/cached.py`) wraps any Tutor and keeps its question text by `pack_id`, and its feedback by `pack_id` and the picked key. A replay then reuses the words the viewer saw.
- The cache lives in the server process, like 2c's prepared-match cache, and is bounded (least recently used). After a restart, a pending question is simply worded again.
- The terminal needs no cache (it doesn't replay within a run), but using it there too is harmless.

**Wording never changes the learning.** The Tutor only supplies text, so for the same answers, the attempts, mastery and question choice must be the same whichever Tutor runs. End-to-end tests check this two ways:
- the demo viewer with the template Tutor, and with a scripted fake model, ends with identical attempt logs, both without a club and supporting one;
- answering through the API with the fake model gives the same log as `btl demo-viewer`, as 2c's equivalence test does for the template.

**Talking to Azure.**
- A `ModelClient` protocol (`tutor/model.py`): `complete(request) -> ModelReply` (text, model name, tokens in and out, seconds), raising `ModelError`.
- `AzureClient` (`tutor/azure.py`) is the only network code. It uses the `openai` SDK with an Entra ID token from `azure-identity`'s `AzureCliCredential(tenant_id=…)`, so it uses the developer's own `az login`. There are no keys: key auth is switched off on the resource.
- **The tenant must be passed explicitly.** Lily's `az` login defaults to another tenant than the one the subscription is in. Checked on 2026-10-17: `DefaultAzureCredential()` returns a token from the wrong tenant, even with `AZURE_TENANT_ID` set, and Azure refuses it. `AzureCliCredential(tenant_id=…)` returns the right one.
- **Responses API with a strict JSON-schema output.** This was checked against the deployment on 2026-10-17 (HTTP 200, about 1–2.5 s per call), so the Chat Completions fallback isn't needed. The api-version is `2025-04-01-preview`.
- **Reasoning effort `none`.** gpt-5.4-nano rejects `minimal` (400 `unsupported_value`); it accepts none, low, medium, high and xhigh. With `none` it uses no reasoning tokens.
- Configuration comes from `BTL_FOUNDRY_ENDPOINT`, `BTL_FOUNDRY_DEPLOYMENT` and `BTL_FOUNDRY_TENANT`. Only `cli/` reads them. Their shape (Lily's real values stay in her own environment, not in the repo):
  - `BTL_FOUNDRY_ENDPOINT=https://<resource-name>.openai.azure.com/`
  - `BTL_FOUNDRY_DEPLOYMENT=gpt-5.4-nano`
  - `BTL_FOUNDRY_TENANT=<tenant-id>`
- Tests never touch the network. They use:
  - a scripted `FakeClient`;
  - a `ReplayClient` over real replies recorded in T7 and committed as `tests/fixtures/tutor-replies.json`;
  - an `httpx.MockTransport` that checks the shape of the Azure request: deployment, schema, and a bearer token rather than a key.

Learned during setup (these go into `docs/setup.md`):
- **Every `az` command needs `--subscription <subscription>`, even with a full `--ids`.** Otherwise `az` uses a token from the default tenant, and Azure answers `InvalidAuthenticationTokenTenant`.
- **A new role takes a few minutes to work** (about 6 here). Until then, calls get 401 `PermissionDenied`.
- **The object id** is the `oid` claim of `az account get-access-token --subscription …`.
- The hub's two older connections are stale, but they don't affect 2b and are left alone:
  - one points to a deleted resource;
  - the other is in another subscription.
- Optional, not done: a small budget alert on the resource group.

## Layout

```
backend/src/btl/tutor/
├── base.py        # Tutor, TutorQuestion, TutorFeedback (the misconception becomes the model's pick when it gives one)
├── slots.py       # unchanged
├── templates.py   # unchanged; the fallback
├── model.py       # ModelClient protocol, ModelRequest, ModelReply, ModelError, FakeClient, ReplayClient
├── azure.py       # AzureClient: the only network I/O
├── prompts.py     # PROMPT_VERSION, system prompt, question/feedback prompt builders, JSON schemas
├── foundry.py     # FoundryTutor(client): prompts → reply → parsed text (no checking)
├── verifier.py    # the checks; verify_question(), verify_feedback() → Check(passed, reasons)
├── verified.py    # VerifiedTutor: primary → verify → repair once → fallback; CheckRecord
└── cached.py      # CachedTutor: the same words for the same question and pick
```
The import rule for `tutor/` (no sim, value, concepts or plant) covers the new modules too. The session fills the takeaway's slots as well as the explanation's, since model takeaways may use slots.

## Risks and cuts

1. **Tenant or quota blocks:** mostly retired. The resource, deployment, role and key-auth switch-off are done, and a call with an Entra token worked on 2026-10-17. What's left is the wrong-tenant token, which `BTL_FOUNDRY_TENANT` handles. The deployment name stays configuration, and all the code is testable without Azure.
2. **The model copies numbers instead of writing slots,** so the pass rate is low. The repair step and prompt iteration in T7 address it. The loop still works on templates.
3. **Latency.** A nano model with reasoning effort `none` (test calls took 1.1–2.4 s), `CALL_BUDGET`, a spinner in the terminal and the page's waiting state. Two calls per question, and the cache stops replays adding more.
4. **An over-strict Verifier.** That costs template text, not correctness; T7 measures each check's share. The basics' football phrases ("second-last defender", "own half") are the likeliest false rejections, so they are allowed from the start.
5. **Prose that's wrong but passes every check** (a false football claim, such as getting a Law wrong in an offside explanation). The hand review and the README's honest limits cover it; the model is told to explain only from the map's text and the facts.
6. **Time.** The plan runs up to the close (see "Schedule"). The cut order protects the terminal and web wiring, which is what the demo shows.

**Cut order if short:**
1. The `--tutor replay` demo mode. `ReplayClient` stays, for tests.
2. The model's misconception pick (the template's pick stays).
3. The repair step: straight to the template.
4. The `comparison` check: forbid comparatives in any sentence with two option slots instead (simpler and stricter).
5. Model-worded questions: feedback only. This also makes the cache matter less, since feedback is asked for once.
